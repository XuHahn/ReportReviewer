7 个优化方案（点击展开详情）

按优先级 P0→P2 排列。优先级依据：收益/成本比 + 实施风险。每个方案独立可实施。

P0

1. Prompt 工程升级：Few-shot + CoT + 动态模板

effort S
当前方式
Stage 1 prompt = system + toc + rules + report
Stage 2 prompt = system + toc + checklist + report

问题:
· 零示例 — AI 自行揣测"什么算问题"
· checklist 全量传入，浪费 Stage 2 token
· original_text 经常改写而非逐字摘录
· 无领域知识注入 (如具体标准条款全文)
· "审核标准"仅是 4 条通用描述
优化方案
1. Few-shot 示例注入
  预置 3-5 条人工标注的"标准审核示例"
  (原文片段 → checklist flag → review_item 完整字段)
  用报告类型 (辐射/传导/谐波) 检索最相关示例
  注入到 Stage 2 prompt 中

2. Chain-of-Thought 推理引导
  Stage 2 增加显式推理步骤:
  "请按以下步骤逐条审核:
   步骤1: 在报告中定位原文段落
   步骤2: 对照适用的EMC标准条款
   步骤3: 判断是否构成不合规
   步骤4: 逐字摘录 original_text (不得改写)
   步骤5: 给出具体修改建议"

3. 动态模板选择
  按 report_category (辐射RE/传导CE/谐波/闪烁)
  选择不同的审核 checklist 和标准条款引用
  • original_text 逐字摘录率预计提升 20-40% (减少 AI 改写)
  • Stage 2 漏检率降低 (few-shot 示范了"什么值得报")
  • 几乎零延迟增加 (仅多 ~500-2000 prompt tokens)
  • 可渐进上线: 先加 CoT 引导 → 验证效果 → 再补 few-shot → 再动态化
实施建议: 从 5 条手工标注的 few-shot 示例开始，存入 prompts.py。在 Stage 2 prompt 中 conditional 注入。预计 1-2 天，零额外依赖。
P0

2. 审核结果缓存：内容哈希 + 增量复审

effort S
当前方式
每次上传完整调用 Stage 1 + Stage 2
同一文件重复上传 → 重新审核 + 重新计费
版本迭代 (V1→V2) → 全文重新审核
无任何去重或复用机制
优化方案
1. 内容哈希缓存
  reports 表加 content_hash 列
  SHA256(plain_text) → 查询是否已有相同内容
  命中 AND 规则/标准未变更 → 直接复用 review_items
  仅重新执行标红 (highlight 依赖 HTML 结构)

2. 增量复审 (版本对比场景)
  V1 → V2: Python difflib 段落级 diff
  仅将新增/修改段落送入 AI 审核
  未变更段落的 review_items 直接继承

3. 缓存失效策略
  规则/标准变更 → 相关缓存标记失效
  prompt_version 作为缓存键的一部分
  • 重复上传延迟从 60-240s 降至 ~1s (直接返回)
  • 版本复审 API 成本降低 60-90% (仅审变更部分)
  • 实现简单: reports 表加 2 列 + save_report 前加 1 个 if
  • 规则/标准变更时需失效相关缓存 → 维护 version 标记
  • 增量 diff 段落边界需处理 → difflib.SequenceMatcher.get_matching_blocks
  • 缓存可能掩盖 prompt 升级效果 → 加 prompt_version 到缓存键
实施建议: 先加 content_hash TEXT + cached_from_report_id TEXT，在 save_report 前检查。Phase 1 只做完全匹配缓存。预计 1-2 天。
P1

3. Token 优化：语义分块替代关键词过滤

effort M
维度当前 (关键词匹配)优化 (Embedding 语义)
分类方式 if keyword in heading.lower(): return priority cosine_similarity(section_embedding, "EMC合规审核要点")
英文报告 中文关键词完全不匹配，所有章节 fallback 到 MEDIUM 多语言 embedding 模型天然对齐，中英文同等精度
误分类案例 "附件A: 补充限值测量数据"→ LOW (含"附件"被直接丢弃) 语义理解整体含义 → 正确识别为 HIGH
超限处理 丢弃的章节信息永久丢失 Map-Reduce 分治: 每章独立 Stage 1 (可并行)，零信息损失
依赖 零外部依赖 sentence-transformers + bge-small-zh (~100MB 本地运行)
  • 章节保留精度从"关键词碰运气"提升到语义理解，预计召回率 +15-25%
  • Map-Reduce 模式彻底消除信息丢弃
  • bge-small-zh 仅 ~100MB，本地 CPU 推理 < 100ms/章节
  • Map-Reduce 增加 Stage 1 调用次数 (但可并行，总延迟 ≈ 单次调用)
  • Embedding 模型对 EMC 领域术语的覆盖度需验证
实施建议: 先用 embedding 排序作为关键词的双保险 (取并集)，积累对照数据后再决定是否替换。预计 3-5 天。
P1

4. 误报抑制升级：Embedding 语义匹配替代 difflib

effort M
场景difflib 结果Embedding 结果
完全一致 相似度 1.0 ✓ 相似度 0.98 ✓
同义改写 "电源线超标" vs "电源线超出限值" → 0.52 ✗ 同一语义 → 0.91 ✓
中英混合 "RE test 30MHz" vs "辐射发射 30MHz" → 0.31 ✗ 多语言对齐 → 0.87 ✓
数值变化 "限值 50 dBμV" vs "限值 48 dBμV" → 0.94 (假阳性!) 数值差异影响 embedding → 0.72 (正确区分)
批量检索 O(n×m) 逐对比较，100 条 × 50 items = 5000 次 FAISS 向量索引 → O(log n)，毫秒级
  • 改写/翻译场景抑制准确率预计从 ~60% 提升到 ~90%
  • 抑制数据越多效果越好 (嵌入空间自然聚类)
  • 与 difflib 可并存: embedding 优先 → difflib 回退
  • 批量检索性能 O(n×m) → O(log n)
实施建议: 在 filter_review_items() 中加 embedding 路径，保留 difflib 作回退。用现有 suppression_patterns 数据建 FAISS 索引。预计 3-5 天。
P1

5. 置信度评分 + 低置信复审机制

effort M
当前方式
AI 返回 review_items 无置信度信息
所有项在前端一视同仁展示
人工标注是唯一的纠错手段
无法区分 "AI 确信的错误" vs "AI 猜测的可能问题"
优化方案
1. Prompt 内置信度
  Stage 2 输出增加 confidence 字段 (0.0-1.0):
  {
    "confidence": 0.92,
    "confidence_rationale": "限值30, 实测33.5,
     明确超标3.5dB, CISPR 25 表5有限值"
  }
  利用 AI 的 self-assessment 能力

2. 自一致性投票 (Self-Consistency)
  Stage 2 跑 3 次 (temperature=0.3)
  3/3 一致 → high | 2/3 → medium | 1/3 → 丢弃

3. 前端差异化展示
  confidence >= 0.85: 正常展示
  0.7-0.85: 黄色边框 + "AI 不确定" 标签
  < 0.7: 折叠 + "需人工确认"
  • 前端可优先处理高置信错误，降低 reviewer 认知负荷
  • 自一致性对 hallucination 有显著抑制作用
  • 置信度数据可用于 prompt 迭代效果评估
  • 自一致性成本 3x，建议仅对 confidence < 0.7 的项触发
  • AI 自评置信度需人工校准 → 积累 200+ 标注后做校准分析
实施建议: 先从 prompt 内置信度开始 (零额外成本)。积累标注数据后做校准分析，再决定是否上自一致性。预计 2-3 天。
P2

6. 可观测性：审核质量仪表盘 + 标注反馈闭环

effort S
当前方式
audit_log: action + employee_id + timestamp
日志: method/path/status/durationMs + reqId
无任何结构化质量数据

无法回答的基本问题:
· AI 审核准确率/召回率是多少?
· 哪些规则最常被人工推翻?
· Stage 1 遗漏率趋势?
· 最近一次 prompt 改动是否提升了质量?
优化方案
1. 标注反馈数据模型
  在 audit_log.detail 中结构化记录:
  {
    "ai_severity": "error",
    "human_status": "false_positive",
    "item_index": 3,
    "rule_ids": ["rule_xyz"],
    "prompt_version": "v3"
  }
  → 可聚合为质量看板

2. 质量看板 (Admin 新增页面)
  核心指标: AI 准确率 / 召回率 / F1
  按规则: 各规则被推翻率排行
  按时间: 30 天趋势 (prompt 迭代效果)
  按审核员: 标注活跃度 + 一致性

3. Diff 日志
  logger.info("data_changed", table=..., column=...,
    old_value=..., new_value=..., reqId=...)
  • 建立质量基线，量化每次 prompt 迭代的效果
  • "常被推翻的规则"可优先放入 few-shot 示例
  • 标注数据积累 → 为未来 fine-tune 提供训练集
实施建议: 先从 Diff 日志开始 (1 天)，再加标注反馈字段 (1 天)，质量看板后续迭代。预计 3-5 天。
P2

7. 弹性与容错：检查点 + 模型级联回退

effort L
当前方式
Stage 1 成功 → Stage 2 超时 → 全部白费
重试 3 次 (2/4/8s 指数退避)
只有 deepseek-chat 单一模型
API 长时间不可用 → 审核完全中断
优化方案
1. 检查点/恢复
  reports 表加 stage1_checklist 列 (JSON)
  Stage 1 完成后立即落盘
  Stage 2 失败 → 从检查点恢复，无需重跑 Stage 1

2. 模型级联回退
  主: deepseek-chat
  回退1: 其他商业 API (moonshot/通义千问)
  回退2: 本地 Qwen2.5-7B 量化版

3. 优雅降级
  Stage 2 不可用时:
    先展示 Stage 1 checklist
    标记 "深度审核待完成"
    后台异步重试
  • 可用性从单点依赖提升到多层容错
  • 检查点避免重复计费
  • 优雅降级保证用户体验不中断
  • 本地模型部署需 GPU (7B 量化可用 CPU 但慢)
  • 模型级联增加架构复杂度，需模型路由器
  • 不同模型输出格式可能不一致 → 需适配层
实施建议: 先做检查点 (加 stage1_checklist 列，Stage 1 后立即 save，2 天)。模型级联和本地部署作为长期方向。预计 5-10 天。
