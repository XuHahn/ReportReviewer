## 1. 目标与边界

系统重构为单一正式审核流程，不再向用户暴露 V1/V2。审核以测试计划定义的本次应做范围为入口，以原始记录证明实际执行，以检测报告证明发布结果，以委托单提供委托与样品事实。测试标准是可选参考知识，不自动扩展本次必做范围。

核心目标：

1. 用证据绑定的关系图表达计划测试项、执行明细、执行实例、参数、结果与文档观察。
2. 解决名称差异、汇总标题、执行明细和重复执行导致的错误合并或错误缺失，例如“电源线瞬态传导抗扰 P2a”与“脉冲 2a”。
3. “没有找到”不得直接等于“没有执行”；证据不足统一保持 `unresolved`。
4. 原生解析负责数字内容，千问视觉负责扫描件、复杂表格和定向补证，DeepSeek 负责文本语义候选，确定性图引擎负责最终结论。
5. 审核人员看到树状任务视图和证据链；完整关系图仅作为高级诊断视图。

四份必需资料：委托单、测试计划、原始记录、检测报告。测试标准可选，未选择时跳过标准参考检查并明确提示。

2026-08-09 业务口径校正：委托单只提供委托与样品基本事实；测试计划定义本次“测什么、怎么测”；原始记录展开每一项执行细则；检测报告汇总发布结果。业务上不预设测试项父子层级。计划明确列出的每一行才是本次基础测试项；脉冲、模式、轮次、样品等在计划未独立列项时只是执行明细或覆盖维度，不能因报告展开方式而额外生成测试项。

## 2. 双层图

### 2.1 公共定义图

公共定义图保存可复用定义，不保存任何文档集执行事实：

- 标准、版本、条款与人工发布快照；
- 测试族、测试子项、方法、参数定义与允许关系；
- 已审核的通用别名和适用范围；
- 证据类型要求和量纲定义。

人工修正默认只影响当前文档集。只有经过显式提升、限定标准/版本/适用条件并发布，才进入公共定义图。历史运行固定使用当时的发布快照。

### 2.2 文档集运行图

每个文档集和每次运行独立保存：

- 文档、版本、页面、区域、表格、行列；
- 测试计划要求；
- 测试执行实例；
- 文档观察和独立声明；
- 参数、结果、异常现象和证据制品；
- 关系候选、门禁结果、人工裁决和审核结论。

禁止跨文档集自动共享执行事实。重复执行必须建立独立实例；样品、模式、日期或轮次不足时保持未决，不得强行合并。

## 3. 权威节点和关系

### 3.1 节点类型

| 节点 | 用途 |
|---|---|
| `test_definition` | 独立测试的公共定义；不决定本次计划范围 |
| `test_subitem_definition` | 兼容公共标准中的显式细分定义；不代表本次业务层级 |
| `test_requirement` | 测试计划中的本次要求 |
| `test_execution` | 某样品、模式、日期和轮次的一次执行 |
| `document_observation` | 来自具体文件、页面、表格或原文行的观察 |
| `claim` | 参数、结果、执行状态等可追溯声明 |
| `requirement_dimension` | 一条要求拆出的条件维度 |
| `coverage_dimension` | 型号、样品、模式、温度、点位等覆盖维度 |
| `instrument` | 设备名称、型号、编号及校准声明 |
| `person_role` | 主检、审核、批准等人员角色与签署状态 |
| `standard_clause` | 已发布标准快照中的条款 |
| `standard_reference` | 文档内标准编号、版本和条款引用 |
| `evidence_artifact` | 波形、照片、截图、表格或其他证据制品 |
| `anomaly_observation` | 啸叫、重启、通信异常等观察现象 |
| `review_finding` | 确定问题、通过、提醒或未决结论 |

所有参与审核比对的参数、结果和执行状态均保存为独立 `claim`，不得覆盖写入执行节点。声明同时保存原始值、归一化值、单位、来源证据、提取方式、模型/规则版本、置信度和人工状态。

## 4. 测试项、执行明细与身份判定

判定顺序：

1. 已发布公共定义图的明确结构；
2. 明确编号、标准结构和稳定名称；
3. 独立参数、次数、结果或表格行证明其可独立执行；
4. DeepSeek 提出带原文证据的候选关系；
5. 程序校验证据存在、节点存在、关系合法且无图约束冲突；
6. 独立证据或第二阶段反驳式复核；
7. 仍不明确则保持 `unresolved`。

计划明确列出的项目建立 `test_requirement`。原始记录和报告中的汇总标题用于基础项目覆盖，表内脉冲、模式、轮次和样品行作为执行明细保存；只有计划也明确把该明细独立列项时，它才可正向证明对应要求。未被计划消费的执行明细不做“计划外测试项”反向报错。

若资料同时出现汇总标题和若干计划明细，只有在全部明细都已与计划逐项一对一匹配，且原始记录与检测报告中的明细也能一一对应时，汇总标题才视为 `summarizes` 关系而不另报第五个项目。任一明细缺失、复用或身份歧义时保持问题或未决，不能用汇总标题吞掉差异。排版缩进只能作为定位上下文，不能建立业务层级。

## 5. 提取与补证

正式链路：

```text
数字文件 -> 原生结构解析
扫描件/复杂表格 -> 千问视觉结构化观察
疑似遗漏 -> 图驱动定位候选页面/区域 -> 局部千问补证
文本身份/关系/适用性 -> DeepSeek 候选
最终状态 -> 确定性图引擎
```

Paddle 退出正式审核链，不生成观察节点、补证或结论。补证结果只能追加，禁止静默覆盖原提取值。

质量门禁包括：

- 文件页数与解析页数一致；
- 表格行数、关键字段和测试项数量合理；
- 原生解析与视觉观察的冲突得到记录；
- 证据可定位到文件、版本、页面和区域；
- LLM 输出通过完整 JSON、schema、证据和数量门禁。

高质量提取自动进入审核；未通过门禁的局部内容进入人工核查。

## 6. 状态与结论门禁

统一状态：

- `confirmed_pass`
- `confirmed_error`
- `unresolved`
- `confirmed_advisory`
- `unresolved_advisory`
- `not_applicable`

缺失升级为 `confirmed_error` 前必须完成：

1. 文件和目标区域覆盖证明；
2. 别名与父子关系扩展检索；
3. 相邻节点、表头、目录和候选页面检索；
4. 局部千问视觉补证；
5. 二阶段复核未找到反证。

补证通过全部门禁后可以自动重算结论，但必须保留旧结论、触发原因、证据变化和模型版本。

## 7. 来源职责

| 来源 | 职责 |
|---|---|
| 委托单 | 委托范围、样品和基本任务事实 |
| 测试计划 | 本次应做范围的唯一入口 |
| 原始记录 | 实际执行、参数和原始结果证据 |
| 检测报告 | 对外发布项目、参数和结论 |
| 测试标准 | 测试结构、方法、参数与符合性参考 |

标准不能证明本次执行，也不能自动向计划增加必做项目。标准明确强制要求而计划遗漏时，DeepSeek 可以生成 `standard_scope_advisory`，但不得直接生成“未执行”，也不直接导致四文档一致性审核失败。

## 8. 通用检查目录

每个检查必须有稳定 `check_id`、适用条件、证据要求、去重键、严重级别、确定性/LLM 职责和对应测试。

### 8.1 核心一致性

| check_id | 检查 |
|---|---|
| `GRAPH-COVERAGE-001` | 计划要求、原始执行和报告发布的项目覆盖 |
| `GRAPH-COVERAGE-002` | 原始执行、报告发布反向闭合到完整计划范围；计划提取不完整时只能待确认 |
| `GRAPH-IDENTITY-001` | 测试项身份、别名和父子关系 |
| `GRAPH-CLAIM-001` | 参数、结果和执行状态的跨来源一致性 |
| `GRAPH-SAMPLE-001` | 样品、型号、模式和轮次覆盖 |
| `GRAPH-CONCLUSION-001` | 汇总结论与明细结果一致性 |

### 8.2 文档内部结构

| check_id | 检查 |
|---|---|
| `DOC-STRUCTURE-001` | 章节/项目编号重复、同号异名、目录与正文不一致 |
| `DOC-STRUCTURE-002` | 项目总数与实际节点数不一致 |
| `DOC-TIMELINE-001` | 单项日期落在报告声明检测区间内 |
| `DOC-TIMELINE-002` | 签发日期不早于最后执行日期 |
| `DOC-TIMELINE-003` | 样品接收日期不晚于试验开始日期 |
| `DOC-REFERENCE-001` | 标准编号、版本和条款引用规范化 |
| `DOC-SIGNATURE-001` | 可配置的主检/审核/批准签署完整性 |
| `DOC-PLAN-REF-001` | 报告引用的测试计划编号与计划自身编号一致 |

编号跳号、日期格式、签字和空字段不得使用全局硬编码规则；必须由模板、机构或任务策略声明适用性。

### 8.3 要求、结果与覆盖维度

| check_id | 检查 |
|---|---|
| `RESULT-DIMENSION-001` | 多条件要求是否逐项给出结果 |
| `RESULT-TYPE-001` | 结果值、单位和量纲是否符合要求类型 |
| `RESULT-EMPTY-001` | 明细结果为空但汇总宣称通过 |
| `RESULT-DUPLICATE-001` | 互斥测试或不同条件间疑似复制粘贴，仅默认提醒 |
| `RESULT-FORMULA-001` | 同一证据行中的读值、修正量、结果和余量重新计算 |
| `RESULT-LIMIT-001` | 结果与同一适用行的明确限值比较 |
| `COVERAGE-MATRIX-001` | 型号、样品、温度、模式、点位等覆盖矩阵缺口 |
| `EVIDENCE-PROFILE-001` | 测试类型要求的波形、照片、量化值等证据是否具备 |

### 8.4 仪器、人员与异常现象

| check_id | 检查 |
|---|---|
| `INSTRUMENT-IDENTITY-001` | 不同设备共用编号或同设备信息冲突 |
| `INSTRUMENT-CAL-001` | 校准有效期覆盖执行日期 |
| `ANOMALY-CONCLUSION-001` | 异常备注与“符合”结论之间是否需要解释 |
| `SEMANTIC-VARIABLE-001` | 变量、人员或名称的疑似误写，仅默认提醒 |

异常现象必须区分 `observed_anomaly`、`standard_violation` 和 `engineering_concern`。未违反计划或已发布标准时不能自动升级为不合格。

### 8.5 默认不作为确定错误

- 日期缺少前导零；
- 中英文标点或大小写差异；
- 普通拼写和错别字；
- “检验/检测”等非关键术语差异；
- 样品编号不连续；
- 空字段或 `/`、`--`；
- 不同测试数据完全相同；
- 产品名称的可解释别名。

这些只能由任务/模板策略开启，或由 LLM 生成带证据的提醒。

## 9. LLM 权限

LLM 负责候选，不直接写确定事实：

- 千问视觉：页面、表格、行列、签署区域和证据制品观察；
- DeepSeek：身份、父子关系、要求拆维度、标准适用性、异常语义和疑似复制模式；
- 图引擎：证据门禁、范围计算、状态转换和最终结论。

每个候选必须返回关系/问题类型、引用证据、理由、置信度和缺失信息。高置信度且通过门禁的关系可以标记 `machine_inferred`；影响最终错误或消除错误时仍需要独立证据或第二阶段复核。

## 10. UI/UX

审核端和管理端合并为单一应用，按角色显示工作区：审核任务、标准知识库、公共定义图、待人工裁决、运行监控、用户权限和系统配置。

首页是任务工作台。新任务流程：

```text
创建任务 -> 上传四份必需资料 -> 自动识别角色 -> 可选标准版本
-> 提取质量门禁 -> 自动审核 -> 人工处理未决 -> 发布与导出
```

审核页默认显示“测试族 -> 子测试 -> 执行实例 -> 参数/结果”的树，以及计划、原始记录、报告和标准参考的横向状态。右侧显示原文证据、页码、截图、声明冲突和关系来源。完整关系图只在高级诊断视图展示。

## 11. 导出与可观测性

- 文档、标准、图、规则和模型版本；
