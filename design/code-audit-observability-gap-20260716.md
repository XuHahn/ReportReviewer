# 代码审计可观测性缺口（2026-07-16）

## 现状

- `logs/app.jsonl` 最后一条业务审核日志停留在 2026-07-08。
- `backend/review.db` 中存在 2026-07-10 完成的真实审核文档集，但本地持久化日志中没有对应的提取、LLM、管线和结果写入事件。
- 2026-07-15 的 `logs/backend.log` 主要包含启动迁移和 HTTP 访问日志，无法还原审核算法执行过程。

## 风险

- 无法用同一个 `reqId` / `set_id` / `run_id` 串联上传、提取、人工确认、审核、结果替换和导出。
- 无法判断零问题结果来自真实通过、LLM 空结果、部分提取、旧结果残留或并发覆盖。
- 生产问题只能依赖数据库最终状态和用户截图，缺少可复盘的中间证据。

## 已实施记录

1. 每轮审核生成并持久化唯一 `run_id`，所有日志同时带 `reqId`、`set_id`、`run_id`。
2. 审核开始时记录输入文档版本、提取状态、提取质量和结构化数据摘要。
3. 每项检查记录 `check_id`、执行状态（passed/failed/skipped/error）、问题数和耗时。
4. LLM 调用记录模型、任务类型、输入/输出长度、JSON 校验状态、重试次数和最终状态，不记录原文正文。
5. 结果写入记录旧问题数、新问题数、是否清空旧结果、事务提交状态。
6. 状态迁移记录旧状态、新状态、触发者和拒绝原因；并发审核记录冲突事件。
7. 日志启动时输出实际日志环境、文件目标和轮转配置，并增加日志写入健康检查。

## 2026-07-16 实施结果

- 开发与生产环境均持久化 `logs/app.jsonl`，启动记录实际环境和文件路径。
- HTTP 未处理异常记录 `reqId`、路径、方法、状态、耗时和错误摘要，并保证上下文释放。
- 每轮审核使用唯一 `run_id`；管线开始、文档输入质量、逐项检查、结果替换和管线完成均可按 `set_id/run_id` 串联。
- 每项检查记录 `check_id`、`passed/failed/skipped`、问题数；LLM 调用继续记录模型、任务、JSON 和重试指标。
- 问题结果无条件事务替换，日志记录旧数量、新数量和零问题清空标记。
- 并发审核采用原子状态抢占，记录冲突；失败恢复到可修订状态，SSE 长调用使用保活帧。
- 上传拒绝、标准上传拒绝、ZIP 资源限制和提取质量降级均有结构化日志。
- 自动化回归覆盖零问题清空、并发抢占、越权、认证进度流、上传上限和提取质量门禁。

## 验收

- 可按任一 `set_id` 完整还原最近一次审核的输入版本、各检查结果、LLM 失败与重试、最终写入结果。
- 零问题、审核失败、超时、重新审核和并发提交均有自动化日志测试。
- 开发与生产环境均能确认日志实际落盘位置，且轮转后仍可检索。
